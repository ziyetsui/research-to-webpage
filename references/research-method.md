# @research 调研思考方法

这份是给人看的压缩版。`@research` 不是一个“总结文档”的角色，而是一套把复杂资料变成可复制调研文档的方法。

## 一句话

先把资料变成地图，再把地图变成模型，最后把模型变成可复用 `.md` 文档。

```text
材料 -> 地图 -> 模型 -> 文档
```

## 核心原则

1. **先定位问题，不急着总结**
   先判断用户是在接手项目、做决策、迁移方法、找缺口，还是要生成执行计划。不同目标决定读资料的深度和输出形态。

2. **先建来源地图**
   调研第一步不是写结论，而是列清楚：读了什么、没找到什么、哪些目录关键、哪些文档和现实不一致。

3. **区分事实、解释、推断**
   事实来自文件和命令输出；解释是把事实连起来；推断是模型判断。推断必须标注，不能伪装成事实。

4. **从 artifact 反推系统**
   看一个项目留下了哪些 artifact：prompt、DESIGN.md、registry、sample、manifest、viewer、lab、docs。稳定出现的 artifact 往往就是系统边界。

5. **抽层，而不是堆信息**
   问清楚哪些层负责多样性，哪些层负责质量，哪些层负责展示，哪些层负责评估。好的系统通常是可组合层，而不是一个大模板。

6. **追问每个决策的 why**
   重要的不是“用了什么”，而是“为什么这样做”以及“这样做排除了什么”。决策背后的排除项，通常就是系统的边界。

7. **找 contracts**
   一个系统能复制，靠的不是灵感，而是稳定契约：命名、文件结构、输入输出、截图证据、registry、质量线、禁止项。

8. **用现有样例反证模型**
   如果抽象出来的模型解释不了现有样例，说明模型太空或错了。先修模型，再谈迁移。

9. **明确不做什么**
   调研不是把所有可能性都塞进 backlog。要标注不值得做、低优先级、和会破坏系统边界的方向。

10. **留下可复用文档入口**
    最后的产物应该能被下一次调用：`/agents`、模板、checklist、prompt、schema、migration guide 或 implementation brief。

## 固定分析框架

默认把项目抽象成：

```text
System = Goal × Layers × Contracts × Artifacts × Evaluation × Expansion Loop
```

- **Goal**：系统稳定产出什么。
- **Layers**：能力或多样性从哪些可组合层来。
- **Contracts**：哪些格式、接口、命名、质量线不能随便变。
- **Artifacts**：每轮工作留下什么证据。
- **Evaluation**：如何判断产物对不对、好不好。
- **Expansion Loop**：如何新增、验证、回填经验。

## 输出形态

一次完整的 `@research` 输出应该包含：

1. **接手结论**：项目是什么，现在到哪了。
2. **来源地图**：读了什么、缺了什么、关键结构是什么。
3. **系统模型**：可迁移的抽象，而不是目录复述。
4. **决策边界**：哪些规则不能轻易改，为什么。
5. **覆盖缺口**：已覆盖、部分覆盖、缺口、跳过项。
6. **Implementation Brief**：具体文件、任务、验收方式，但作为交给 `@webpage` 的文档。

## 判断质量

好的调研结果应该满足：

- 能解释现有项目为什么长这样。
- 能指导下一步由谁做什么。
- 能说明什么不该做。
- 能迁移到另一个项目。
- 能变成 agent、模板或流程。

如果只能复述文档，还不是 `@research`；如果能让下一次调研和实现交接更快、更准、更稳，才算完成。
